# Linux 中文/拼音输入法项目汇总与开发参考

> 调研对象：`/home/mlran/downloads/im/inputmethods` 下全部 **25 个 git 仓库**（另有 2 份讨论稿和 1 个模型包）。
> 调研方式：逐仓库读 README/架构文档/关键源码，核查目录、提交时间、体积、许可与框架引用。
> 数据截至：2026-11-18。体积为去掉 `.git` 的工作树大小；Star 数为 GitHub API 实时读取。

---

## 0. 先看结论（TL;DR）

**这批项目的本质**：它们不是 25 个同质项目，而是围绕中文输入法的 **4 条技术路线 + 1 套数据生态**：

| 路线 | 代表项目 | 一句话 |
|---|---|---|
| A. Rime 方案/数据 | rime-ice、rime-frost、万象、五笔86 | 只写 YAML 和词库，跑在现成 librime 上 |
| B. Rime 内核 + 薄前端 | librime、ibus-rime（+ 生态外的 fcitx5-rime/fcitx-rime） | 用一个 C++ 引擎，前端各写几百行 |
| C. 自研引擎 + 多前端 | msime、WindInput、Sime、鲸鱼 | 自己写算法，用 C ABI/IPC 接多个框架 |
| D. AI 增强 | bangke-ai-predict、CTranslate2、Sime 的 GRU | 在候选层加模型，不改主链路 |

**三个必须知道的事实：**

1. **25 个仓库里没有任何一个同时支持 ibus + fcitx4 + fcitx5。**
   - 同时支持 IBus + Fcitx5 的只有 **msime** 和 **鲸鱼 whale-panel**；
   - 只做 Fcitx5 的是 **WindInput、Sime、msime 的 Linux 入口之一**；
   - 只做 IBus 的是 **ibus-rime**；
   - **fcitx4 一个都没有**。fcitx4 已停止演进，这批项目全部放弃。
2. **想做三框架，正确姿势不是"写三遍"，而是"一个内核 + 三个薄适配器"。** msime 的四层架构（纯引擎 / 会话运行时 / 版本化 C ABI / 原生前端）是本地最好的范本。
3. **如果只想最快做出可用产品，别自己写引擎**：基于 librime 写方案与词库，ibus/rime、fcitx5-rime、fcitx-rime 三个前端是现成的，工作量从"年"降到"月"。代价是 UI 定制弱、前端是 GPL。

## 2. 分组详解

### 2.1 deps：Rime 底座与词库（9 个）

这是整套生态的"地基"，也是你最该先读的一组。

#### librime —— 事实上的中文输入法标准内核

- **是什么**：Rime 输入法引擎，C++17，约 3.4 万行，BSD-3，4723 星，仍在活跃维护。
- **架构**：`algo`（拼写代数、音节切分、编码器）、`config`（YAML 编译，支持 `__include/__patch/__append/__merge`）、`dict`（Prism 双数组 Trie、Table 词条表、UserDictionary/LevelDB、Corrector）、`gear`（所有具体组件）、`lever`（部署与编译流水线）。
- **核心模型是"管道"**：按键 → `Processor` 链 → `Segmentor` 切段 → `Translator` 出候选 → `Filter` 过滤排序 → `Menu` 合并 → 上屏。所有组件都由 schema YAML 里的 `engine/processors|segmentors|translators|filters` 声明式装配。**这是"方案即配置"的精髓，也是最值得抄的设计。**
- **拼音主路径**：`ScriptTranslator::Query` → 用 Prism 建音节图（SyllableGraph）→ 词典 + 用户词典查询 → `Poet::MakeSentence` 在词图上做整句搜索。
- **数据格式**：`.dict.yaml` 头部声明列（默认 `text/code/weight`）、`import_tables`、`use_preset_vocabulary`；编译产出 `.table.bin`（词条）、`.prism.bin`（拼写→音节）、`.reverse.bin`（反查）。
- **对你有用的点**：C API 稳定且带 ABI 版本探测（`RIME_STRUCT_INIT`）；字典编译思想（离线建索引、运行时 mmap）；Poet 词图搜索；用户词典与部署流程。

#### ibus-rime —— 最好的 IBus 前端教材

- 只有约 1000 行 C，但把 IBus engine 该做的事做全了：注册 component XML、每 engine 一个 Rime session、按键直传 `process_key`、`update()` 里处理 preedit/aux text/候选表/翻页/点击、属性菜单做中英切换与重新部署。
- **关键细节**：IBus 的 keyval/modifier 与 librime 的 X11 mask 天然兼容，几乎不用转换；支持 `composition`/`preview` 两种行内预编辑。
- **这是你写 IBus 前端时最短的参考路径**（注意 GPL-3.0，闭源项目应按接口重写而不是复制）。

#### OpenCC —— 简繁与地区词

- 词典驱动的确定性转换，Apache-2.0。配置 JSON 定义转换链（`s2t`/`t2s`/`s2tw`/`s2hk`），词典编译成 `.ocd2`（Darts 双数组）。
- 数据量：`STCharacters` 4012 条、`STPhrases` 49277 条、`TSCharacters` 4148 条、`TSPhrases` 498 条，另有 TW/HK 变体与日文新字体。
- **用法**：候选生成后做"词组优先、单字兜底"的链式转换；注意简繁开关要和字符集过滤联动，否则港台字形会被常用字集过滤掉。

#### pinyin-data —— 单字读音的权威底表

- 44,440 条，其中 8,633 个多音字；格式 `U+4E2D: zhōng,zhòng  # 中`。来源是 Unihan、汉典、通用规范汉字表 8105、CC-CEDICT。
- **只给单字读音，不含词、不含词频**。适合生成字表；词级数据必须另找。

#### plum —— Rime 包管理器

- 920 行 Bash，用 `user/repo@branch:recipe:key=value` 拉取并安装配置包，支持 `install_files/download_files/patch_files`。
- 最有价值的是 `scripts/frontend.sh`：它内置了各前端的用户目录映射（ibus-rime → `~/.config/ibus/rime`，fcitx5-rime → `~/.local/share/fcitx5/rime`，fcitx-rime → `~/.config/fcitx/rime`）。**你做多前端时一定会遇到"同一份数据放哪"的问题，这张表可以直接用。**

#### rime-essay —— 一元词频先验

- 442,685 行 `词<TAB>权重`，不是 n-gram 模型。单字 2 万、二字 17 万、三字 11 万、四字 12 万。
- 作用：给没有权重的词条兜底词频，并作为预设词库扩充词量。**冷启动做排序时，这是最省事的一元先验。**

#### rime-ice（雾凇）/ rime-frost（白霜）—— 两套最流行的拼音词库

| 维度 | rime-ice | rime-frost |
|---|---|---|
| 主词典行数 | 约 193.5 万 | 约 106.8 万 |
| 组成 | 8105 字表 + base 55.8 万 + ext 33.9 万 + tencent 98.2 万 | 8105 + base 37.7 万 + ext 23.6 万 + GB18030 5.6 万 + tencent 34.3 万 |
| 特色 | 8 套双拼、29 个 Lua 扩展、部件拆字 | 7.45 亿字语料重算词频、24 个领域"细胞词库"共 134 万、任意位置辅助码、错字错音表 |
| 许可 | GPL-3.0 | GPL-3.0 |

- `speller/algebra` 段落是学习**双拼映射、模糊音、纠错派生**的最佳样本：它用代数规则从全拼派生双拼，而不是维护多份词库。
- 两者的 `tencent` 词表只有"词 + 权重"、没有注音，靠字表自动注音——这是"大规模词表低成本接入"的标准做法。

#### rime-wubi86-jidian —— 形码路径参考

- 8.9 万词条，MIT。展示 `table_translator` 的用法、`encoder.rules` 自动生成多字词编码、`stem` 列做第四码。
- 对"拼音 + 形码辅助码"很有参考价值。

### 2.2 shuishan-msime：六平台产品化范本（3 个）

**这是本地工程完成度最高的一组**，也是最值得作为"产品级架构"参考的。

#### msime

- **定位**：水杉输入法，覆盖 Windows/macOS/Linux/Android/iOS/HarmonyOS。Linux 版本 0.16.1，macOS 0.60.0。GPL-3.0，但**引擎单独 MPL-2.0**，允许闭源应用嵌入。
- **技术栈**：Rust 约 65 万行（23 个 crate）+ Linux 宿主 C++ 约 6.3 万行 + React/TS 设置界面。
- **四层架构**（`docs/ARCHITECTURE.md`）：
  1. `crates/engine`：纯算法，不感知框架；
  2. `crates/input-runtime`：会话、焦点、分页、代次、异步调度；
  3. `crates/host-api`：版本化 C ABI（132 个导出，ABI 3），整数句柄 + 线程绑定 + JSON 响应；
  4. `platforms/linux`：IBus 可执行 + Fcitx5 addon 两个并列入口。
- **Linux 两个入口是并列的，不是主从**：IBus 独立进程（崩了不影响 daemon），Fcitx5 addon 加载进 fcitx5 进程（崩了所有应用一起失去输入法）。这个差异必须写进你的风险表。
- **引擎算法**：最少音节 DP 切分 → SQLite 词典（`tbl_<音节数>_<首字母>`，184 张表）→ 同音/简拼/模糊/纠错 → 词格 Viterbi 束搜索（beam 32）→ 一元词频 + 二元 MSNG（100 万条，11.44MB）+ 三元后处理重排 → 可选神经重排（4.28MB）。
- **学习机制**："代次目录 + journal 回放"：资源只读，用户目录放工作副本，学习写 journal，换词库时新建代次并回放。这是本地最稳的词库更新方案。
- **工程细节**：604 个金样测试文件；复现 libc++ 的 `partial_sort` 保证候选顺序确定；`scripts/verify-local.sh` 一键门禁。
- **代价**：两套 C++ 前端各约 1 万行，共享的只是 ABI，不是 UI。

#### msime-dictionary

- 17 个上游、63 个文件、约 229MB，用 `upstream.lock.json` 锁 commit + 逐文件 SHA-256。
- 真正的构建器在 msime 仓的 `crates/dict-builder`，21 个阶段（全拼→重加权→地名→自定义→读音修正→否决→权重覆盖→五笔→短语→英文→Emoji→符号→日文→n-gram），`builder.lock.json` 固定构建器版本。
- **许可门**：`licensing.rs` 默认排除无再分发授权的输入，发布流程断言 `includes_unlicensed_inputs=false`。
- 这是"数据与代码分离、可复现构建"的教科书。

#### msime-docs

- 跨仓职责总表、四步输入流程（收键 → 引擎 → 前端渲染 → 异步结果归属校验）、安全模型（哪些在进程内、哪些出网、已知薄弱处）。
- 注意：文档版本表滞后于代码，判断状态要看 tag 和 `platforms/*/version.txt`。

### 2.3 wanxiang：数据与方案（2 个）

#### rime-wanxiang

- 万象拼音，5156 星，Rine 方案集合，CC BY 4.0。**35G 几乎全在 `.git`**（单个 pack 34.16GiB，历史上有 18032 个 blob、6000 多个超 10MB），工作区词库只有约 60MB。原因是每日提交大词库 + 模型文件曾入库。**用 Release 或浅克隆即可，不要拉全历史。**
- 四个发行版：Base（全拼/双拼，完整 Lua）、Pro（双拼 + 多套辅助码）、Lite（无声调轻量）、Pure（无 Lua，面向 fcitx4-rime/Win7）。
- 能力：全拼/14 套双拼（通过 algebra 转写，不是多份词库）、直接/间接辅助码、简繁 s2t/s2hk/s2tw、中英混输、九键。
- 28 个 Lua 文件、约 2.2 万行：日期农历节气、金额大写、科学计算器、Unicode 符号搜索、上下文调频（1/2-gram，5 秒超时）、无感造词、字符集过滤。
- 语法模型是 `wanxiang-lts-zh-hans.gram`（librime-octagram，静态前缀树 + mmap），不是神经网络。

#### rime-wanxiang-data

- 真正的数据源仓：`dicts/`（jichu 159 万条带调词、zi 5.1 万行单字、en 7.3 万、诗词 33.5 万、地名 8.9 万、化学/药品/医学/名人/艺人/多音/错音）、`dicts_hant/` 繁体镜像、`pinyin_data/`、内置 pypinyin 0.53.0、`tools/`（语料清洗、分词、语法模型构建、评测）。
- 词条格式：`词<TAB>带调拼音<TAB>词频`，用"词 + 拼音"双键统计词频，能区分多音字——**这是比"字表 + 全局词频"更正确的数据模型**。
- msime-dictionary 已改为锁这个仓的 15 个文件，说明它是被下游认可的上游。

### 2.4 wind：服务化 + 薄壳（4 个）

- **WindInput**：1646 星，Rust 约 49.6 万行、20 个 crate。核心设计是**引擎与渲染都在独立服务进程**，前端只做三件事：按键转协议、上屏/预编辑写回、贴图。
  - 协议走 Windows 命名管道 / Unix Socket，候选窗由服务端 tiny-skia 光栅化成 BGRA 位图，经 POSIX 共享内存 + 命中矩形推给前端。
  - Linux **只做 Fcitx5**（`wind_linux` 是 C++17 addon，X11 用 xcb、Wayland 用 layer-shell/input-method-v2），明确写"IBus 之后再议"。
  - 引擎：414 音节 Trie + DP 最大匹配切分、模糊音 13 组、词格 Viterbi、三层排序（引擎内 → 协调器 → 频率重排）、用户词/临时词/草稿/词频/Shadow 全部落 YAML 文本。
  - 词库不在仓库，由脚本从 rime-frost/五笔/pinyin-data/OpenCC 生成，编译成 `.wdat` 双数组 Trie（mmap）。
- **wind-ui-rust**：通用 GUI 库（MIT/Apache），**不是输入法候选窗**，是做设置器的；别被名字误导。
- **wind-setting**：清单驱动（4595 行 `settings_manifest.toml`），所有设置项、控件、默认值、联动都从清单生成；与引擎走 JSON-RPC，只发 diff，不直接改配置文件。
- **windinputdocs**：Next.js + Fumadocs 静态站。架构文档其实在主仓 `docs/architecture/`，不在文档站。

**可借鉴的核心**：`UiCommand` 语义统一（40+ 变体），三个平台前端共享同一套命令；配置键注册表是唯一真相源，设置器与文档都从它派生。

### 2.5 shiyu-sime：紧凑端上引擎 + 神经重排（3 个）

- **Sime**：Apache-2.0，C++20 核心仅约 7800 行，但完成度高。定位"完全端上，准确率对标商业输入法"。
- **算法不是"先切分再查词"，而是直接在字节格上枚举边**：对每个位置做拼音前缀搜索（允许跳过字符匹配到下个 `'`），天然支持全拼/简拼/混拼/缺省音节；再补扩展边。
- **词典**：自定义 mmap 二进制，26.2 万词，两个 DAT（拼音、英文），UTF-32 文本表零拷贝。
- **语言模型**：三元 IAD（插值绝对折扣），保留约 250 万二元、100 万三元；16-bit 概率 + 8-bit 回退权重分位量化；SoA 布局 + O(1) 一元索引。
- **GRU 重排**：单层双向 GRU（hidden 64）+ 32 维 embedding，ncnn CPU 单线程 INT8，**只重排 Top-10**。延迟只增加 0.007ms（全拼）、0.026ms（九键），句准确率 +5.07pp。这是"小模型只做重排"的典范。
- **用户学习**：用户 bigram 与主 LM 在概率空间混合，`max(lm, mixed)` 保证"只会变好不会变差"，权重 0.2，8192 段上限，带词汇签名防止模型换代后 TokenID 错位。
- **前端**：Linux 只做 Fcitx5（`InputMethodEngineV3`，同进程静态链接 `sime_core`，无 IPC），Android JNI、macOS C ABI。
- **dictcut**：按"删掉该词造成的似然损失"裁剪词表（删边重跑 DP），不是按词频 Top-N；35 万词基线，产出 12/18/24 万档。
- **短板**：模型路径硬编码 `/usr/share/sime`；每次按键重建整张格，无增量解码；文档与代码有若干不一致。

### 2.6 llm：AI 候选（3 个 + 模型）

- **bangke-ai-predict**：librime 插件（`ai_predict` 模块），C++17，把"已上屏上下文 + 当前拼音"喂给本地 seq2seq 模型，产出汉字候选插到第 2 位。
  - 模型输入格式：`window_text + <pinyin_start>拼音</pinyin_start>`，输出 `<hanzi_start>…</hanzi_start>`。
  - **异步设计是关键**：`Query()` 未命中缓存时只投递任务并立刻返回，后台线程防抖 200ms、单槽缓存、在途去重；worker **绝不调用** `Compose()`/任何引擎 API（注释里记了真实崩溃栈），只写缓存 + 置 `pending`；前端轮询到 pending 后自己触发一次刷新。
  - 候选注入用 `ShadowCandidate` 提升位置或新建整段跨度候选；跨度必须用当前 segment 的 range，否则会把 commit 切坏。
  - 协议：`ai_predict/pending`、`_comment_highlight`、`_refresh_ui`、`ai_predict/client_context`（前端可推入宿主光标前文本，比 `commit_history` 更准）。
  - 性能：CT2 int8 + RUY，4 线程，p50 约 89ms，max 5.6s（超时丢弃），启动时自检失败就直接关闭 AI。
- **bangke-librime**：与上游差异极小（引擎代码约 70 行）：`BUILD_TOOLS` 开关、`RIME_PLUGIN_LIST` 显式空插件列表、Boost 1.74 兼容、glog 0.6 兼容、`Schema::set_page_size()` 动态分页。**它证明了"librime 插件化不需要改内核"。**
- **CTranslate2**：Transformer 专用推理库，支持 seq2seq/decoder-only/encoder-only；int8 逐行对称量化，CPU 走 MKL/oneDNN 或 RUY；4 线程下比 PyTorch int8 快 2 倍以上。选它的理由：可静态链接、无 Python、CPU 够快、依赖少。
- **模型包**：`zh-base-ct2-int8.tar.gz` 是 227MB 的 BART 类自定义 seq2seq（encoder 6 层 / decoder 8 层），词表 16,776 = BPE 6,400 + 10,000 汉字 + 366 拼音音节。**专为简体拼音输入定制，不是通用 LLM。**
- 两份 md 是 Squirrel 前端为插件开挂载点的提案：#1124（日志目录、comment 配色、异步刷新）与 #1143（`_` 前缀保留属性协议）。核心思想：**未知保留 key 静默忽略，保证向后兼容。**

### 2.7 jingyu-whale：libpinyin + 双前端（1 个）

- 鲸鱼输入法，MIT，Linux 专用，**IBus + Fcitx5 双前端 + GNOME Shell 跟随光标面板**。
- 结构：`whale-core`（Rust，封装 libpinyin，`rlib+staticlib+cdylib` 三种产物）→ `whale-engine`（Rust 手写 IBus FFI）/ `fcitx5-whale`（C++ addon）→ `extension/`（GJS 面板）经 `/tmp` 文件 IPC 通信。
- 说明：**libpinyin 是另一条成熟路线**。生态外，`ibus-libpinyin` 与 `fcitx5-chinese-addons` 的拼音引擎都基于它，也就是说"一套引擎 + 三个框架"在 libpinyin 上已经成立过（fcitx4 时代还有 fcitx-libpinyin）。但 libpinyin 算法代际较老，长句和词频质量不如新方案，且 GPL-3.0。
- 鲸鱼自己的工程亮点：整句 Viterbi（长度 ≥6）+ 简拼索引 + 部分提交（只消费候选覆盖的音节前缀）+ 候选最多 60 个 + 上次选择置顶；Fcitx5 初始化放后台线程，避免大词库 mmap 阻塞主循环；GNOME 下用 `protocol_to_stage_rect` 做光标定位并夹紧屏幕。
- `fcitx5-theme/` 只是 classicui 主题，不是前端本身。

## 3. 横向对比：四条路线怎么选

| 维度 | A. 纯 Rime 方案 | B. librime + 自研前端 | C. 自研引擎 + C ABI | D. 封装 libpinyin |
|---|---|---|---|---|
| 代表 | rime-ice/万象 | ibus-rime 改 | msime/Wind/Sime | 鲸鱼 |
| 出可用版本 | 1–2 人月 | 3–6 人月 | 12+ 人月 | 2–3 人月 |
| 三框架支持 | 现成（ibus-rime/fcitx5-rime/fcitx-rime） | 需自己写 3 个前端 | 需自己写 3 个前端 | IBus/Fcitx5 现成，fcitx4 需适配 |
| UI/交互可控性 | 低（受 Rime 前端限制） | 高 | 最高 | 中 |
| 算法可控性 | 中（受 librime 组件模型限制） | 中高 | 最高 | 低 |
| 许可风险 | 前端/词库 GPL | 内核 BSD，前端自写可控 | 自己决定 | libpinyin GPL |
| 适合谁 | 想快速验证方案、做词库产品 | 想要自有品牌 + 可控 UI | 要做长期产品、多平台 | 想快速有可用拼音 |

**我的建议：**

- **如果目标是"尽快有能用的三框架拼音"**：选 B。用 librime 做内核（BSD，可闭源链接），自己写 IBus/Fcitx5/fcitx4 三个薄前端，词库用 rime-ice 或万象。这样你既不受 Rime 前端 UI 的限制，又不用重写引擎。
- **如果目标是"做一款有差异化的产品"**：选 C 的架构，但**第一版复用 librime 或 libpinyin 的算法与数据**，先跑通前端和产品闭环，再逐步替换内核。msime 就是这么长出来的。
- **如果只是想做输入方案/词库**：选 A，别写代码。
- **任何路线都可以横向加 AI 候选**：按 bangke 的"同步词典先出、异步模型后补"模式，不要改主链路。

## 4. 面向"ibus + fcitx4 + fcitx5"的架构建议

### 4.1 推荐分层（直接对标 msime，但精简）

```
┌─────────────────────────────────────────────────────────┐
│ 前端适配层（每个框架一份，薄）                            │
│  ibus-engine  │  fcitx5-addon  │  fcitx4-addon           │
│  只做：按键映射 / 预编辑 / 候选渲染 / 上屏 / 光标位置      │
└───────────────────────┬─────────────────────────────────┘
                        │ 版本化 C ABI（或 IPC）
┌───────────────────────▼─────────────────────────────────┐
│ 会话运行时：session / focus / 分页 / 代次 / 异步任务       │
└───────────────────────┬─────────────────────────────────┘
┌───────────────────────▼─────────────────────────────────┐
│ 纯引擎：切分 → 词典 → 词图 → 语言模型 → 学习              │
│  （不 include 任何 ibus/fcitx 头文件）                    │
└───────────────────────┬─────────────────────────────────┘
┌───────────────────────▼─────────────────────────────────┐
│ 数据层：只读资源（mmap）+ 用户目录（可写）                 │
└─────────────────────────────────────────────────────────┘
```

**硬性约束（照着做能省几个月）：**

1. 引擎层**零框架依赖**，可单独跑 CLI 和单元测试。
2. C ABI 用**整数句柄**，不要暴露 C++ 对象；句柄绑定线程，错误线程调用返回错误而不是崩溃。
3. 候选选择携带 `{session, generation, index}`，拒绝旧代次和越界索引。
4. 返回值区分 `handled`（是否吃键）和 `commit`（上屏文本），不要混在一起。
5. 前端**不持有输入状态**，只持有句柄和渲染所需的最小快照。

### 4.2 三个框架的适配要点

| 项 | IBus | Fcitx5 | Fcitx4（legacy） |
|---|---|---|---|
| 形态 | 独立进程 + D-Bus | 共享库 addon，加载进 fcitx5 进程 | 共享库 addon，加载进 fcitx 进程 |
| 入口 | `IBusEngine` 子类 + component XML 装到 `/usr/share/ibus/component/` | `InputMethodEngineV2/V3` + `addon/*.conf`（`Type=SharedLibrary`） | `FcitxIMClass` + `FcitxInputState` 这一代接口 |
| 会话 | 每个 engine 实例一个 Rime/引擎 session | 每个 `InputContext` 一个 `InputContextProperty` | 每个 IC 一份状态 |
| 按键 | `process_key_event`，注意 release mask | `keyEvent`，`KeyEvent` 自带状态 | 旧式 key event |
| 预编辑 | `update_preedit_text`（支持行内/光标） | `InputPanel::setPreedit/setClientPreedit` | 写 `FcitxInputState` 的 preedit |
| 候选 | `IBusLookupTable` + 翻页/点击回调 | `CandidateList` + `updateUserInterface` | 旧 candidate word list |
| 光标定位 | `set_cursor_location` | `ic->cursorRect()` | 旧接口 |
| 崩溃影响 | 只挂自己 | **拖垮整个 fcitx5** | 拖垮整个 fcitx |
| 最低版本 | 1.5.20+ | 5.0.20+（5.1.x 有更多 UI 能力） | 已 EOL |
| 参考 | `deps/ibus-rime/rime_engine.c` | msime `platforms/linux/fcitx5/`、wind `wind_linux/`、鲸鱼 `fcitx5-whale/` | 本目录无；参考上游 fcitx-rime（已归档） |

**关于 fcitx4 的现实建议：**

- fcitx4 只存在于 UOS 20、麒麟 V10 等老政企系统。上游早已停止演进，新项目不应把它当一等公民。
- 如果必须支持：写一个**最小的 fcitx4 addon**，复用同一个 C ABI 和同一套候选模型，**不要为它单独做一套 UI**；或者干脆只提供 IBus 并引导用户切换。
- 注意 fcitx4 与 fcitx5 的 addon 不能共存于同一进程模型，打包时要做互斥/替代关系（参考鲸鱼的 `Obsoletes/Provides` 做法）。

**候选窗的额外提醒（比框架 API 更容易踩坑）：**

- X11：override-redirect 顶层窗 + `_NET_WM_WINDOW_TYPE_POPUP_MENU`；有合成器用 ARGB，没有就用 XShape 抠圆角。
- Wayland：**没有全局坐标**。要么走 `input-method-v2` 的 popup、要么 `wlr-layer-shell`、要么像鲸鱼一样做 GNOME Shell 扩展。GTK 普通窗口做候选窗在 Wayland 下焦点和定位都不可靠。
- 多显示器 + 分数缩放 + 任务栏遮挡：要按显示器工作区夹紧，并给上下翻转留策略。
- 前端自绘 vs 框架原生：自绘可控但三份代码；原生省事但样式受主题限制。折中方案是"服务端渲染位图 + 前端贴图"（wind）或"只做数据协议 + 外部面板"（鲸鱼）。

### 4.3 引擎实现顺序（每一步都可独立验收）

| 阶段 | 做什么 | 验收标准 | 参考实现 |
|---|---|---|---|
| 1 | 音节表 + 全拼切分（最少音节 DP） | 对评测集拼写 100% 可切分，歧义串给出多路径 | msime `pinyin/segment.rs`；wind `pinyin/dag.rs` |
| 2 | 词典索引（SQLite 或 mmap DAT） | 单字/词查询 p99 < 1ms；冷启动 < 200ms | msime `dictionary/pinyin.rs`；sime `convert.cc` |
| 3 | 同音词、前缀、简拼、模糊音 | 常用 500 词 Top-1 达基线 | wind `pinyin/{abbrev,fuzzy}.rs` |
| 4 | 词图 + Viterbi/Beam 整句 | 10 字句子 Top-1 ≥ 70% | msime `lattice/decode.rs`；sime `sime.cc` |
| 5 | 二元/三元语言模型 | 整句 Top-1 再 +5~10pp | sime IAD；msime MSNG |
| 6 | 纠错、错音、双拼、辅助码 | 错拼 1 键仍能出正确候选 | rime-ice algebra；万象 duoyin/cuoyin |
| 7 | 用户学习 + 词库更新 | 学习后常用词位次上升，换代次不丢数据 | msime journal；sime `user.cc` |
| 8 | 神经重排（可选） | 只重排 Top-10，p95 增加 < 1ms | sime GRU；msime neural rerank |
| 9 | AI 候选（可选） | 首帧不等模型；AI 候选 100–300ms 内出现 | bangke-ai-predict |

**不要跳步**：第 7 步之前不要做模型，否则你无法判断效果来自算法还是模型。

#### 自建数据时的建议

1. **数据模型用"词 + 拼音序列 + 对数词频"三列**，不要只存"词 + 词频"。多音字必须按词注音，否则"长江/长大"永远错一个。
2. **冷启动**：用 pinyin-data 生成字表 → 用 essay 补一元权重 → 用 rime-ice/frost/万象做词表 → 用 OpenCC 做简繁。四步能拼出一个可用词库。
3. **构建期裁剪**：词表不是越大越好。dictcut 的思路（按删除造成的似然损失裁剪，保留单字）比"按词频砍尾"更能保住覆盖率。目标控制在 20–50 万词，首屏和内存都更友好。
4. **n-gram 训练**：中文维基 dump（CC-BY-SA）+ 清洗 + 分词 + 计数 + 剪枝。参考 sime 的 `pipeline/Makefile`（cut→count→construct→compact）和 msime 的 Ngram 阶段。
5. **评测集先建**：至少 500 条真实输入日志（拼音 → 期望候选），分"常用词/长句/错拼/简拼/中英混输"五类。没有评测集，所有优化都是盲调。
6. **锁上游**：每个数据源固定 repo + commit + 逐文件 SHA-256，构建器版本也锁。msime-dictionary 的 `upstream.lock.json` + `builder.lock.json` 是标准做法。
7. **维护者清洗表独立于上游**：否决词、权重覆盖、敏感词放自己的 `curation/`，构建时施加，不改上游文件——这样上游更新不会覆盖你的调整。

### 4.5 中英混输怎么设计

这是中文输入法的高频痛点，建议单独设计，不要塞进中文词图。

| 问题 | 做法 | 参考 |
|---|---|---|
| 英文词从哪来 | 独立英文词表 + 词频；不要和中文词混在一张表 | 万象 `en.dict.yaml`；rime-ice `melt_eng` |
| 什么时候进英文模式 | 显式切换 + 自动识别（连续字母 ≥N、大写开头、遇到 `@ / : .`） | wind `EngineType::English` |
| 词间空格 | 状态机：第二个词起自动加空格；空格/回车打断；5 秒超时；URL/路径延迟加空格 | 万象 `super_english.lua` |
| 大小写 | 首字母大写、全大写、驼峰三种推导；保留用户原样输入 | 万象 `super_english.lua`；msime English 阶段 |
| 混合词条 | 独立表（`AD钙奶`、`Type-C`、`1000wclips`），不进中文整句词图 | 万象 `mixed.dict.yaml` |
| 标点 | 中文模式全角、英文模式半角；`@ . / :` 触发英文上下文 | 各项目通用 |
| 编码冲突 | 英文和拼音共用字母键，靠"是否成词 + 上下文"或显式 shift 决策 | 建议：默认拼音优先，英文候选并排给出 |
| 纯英文输入法 | 不做整句转换，做**词补全 + 拼写纠错 + 下一词预测**；词表用 SCOWL/Hunspell | SCOWL；msime `msime-english.db` |

**关键判断**：如果用户系统里已经有 XKB 英文布局，独立英文输入法的价值很低；真正的需求是"中文输入法里的临时英文/中英混输"。把精力放在混输的空格、大小写、标点切换上，收益远大于做一个纯英文 IME。

### 4.6 里程碑与验收

| 里程碑 | 交付 | 验收 |
|---|---|---|
| M0 选型 | 架构决策记录（内核路线、许可、目标框架） | 能在 IBus 和 Fcitx5 里各跑通一个 echo engine |
| M1 数据 | 可复现的词库构建（锁文件 + 脚本） | 从零构建两次，产物 SHA-256 一致 |
| M2 引擎 MVP | 切分 + 词典 + 整句 | 评测集 Top-1 ≥ 70%，p99 按键延迟 < 10ms |
| M3 Fcitx5 | addon 完整可用 | 候选/预编辑/翻页/点击/光标定位/中英切换全通过 |
| M4 IBus | engine 完整可用 | 同上，且崩溃不影响 ibus-daemon |
| M5 学习与配置 | 用户词、调频、设置界面 | 重启不丢数据；词库升级后学习数据可迁移 |
| M6 fcitx4 | legacy addon | 老系统可用；或明确记录"不支持"及替代方案 |
| M7 性能与打包 | deb/rpm、内存/启动优化 | 冷启动 < 300ms，常驻内存 < 80MB（含词库 mmap） |

## 5. 拼音与英文输入法的专项提醒

### 5.1 拼音的 10 个坑

1. **多音字**：必须按"词 + 读音"建索引，不能按字。否则"银行/行走"只能对一个。
2. **简拼歧义**：`xian` 可以是 `xian`、`xi'an`、`x ia n`。要有音节边界策略和候选代价，不能只靠最长匹配。
3. **切分歧义**：`fangan` = `fang an` / `fan gan`。DP 要保留多路径，让语言模型决定，而不是切分阶段就砍掉。
4. **模糊音是双刃剑**：加上 `zh/z`、`n/l`、前后鼻音后，召回变高但精确率下降。要按用户开关分组，并给模糊匹配降权。
5. **纠错要能撤销**：把 `nihao` 打成 `nihap` 仍出"你好"是加分项，但用户明确选了别的词后要记住，不要反复纠。
6. **整句与词的冲突**：整句候选不要简单插到第 0 位，否则会出现"白一百顺"这类错误。要有插入位置规则和长度惩罚。
7. **词库不是越大越好**：低频词会挤占候选位、拖慢加载。20–50 万词 + 好的词频，通常优于 200 万词 + 垃圾词频。
8. **排序要稳定**：同分候选的顺序必须确定（按 weight → natural_order → code → 文本），否则每次按键候选都在跳，用户无法形成肌肉记忆。
9. **用户学习要"只能变好"**：用户数据权重过高会污染强模型。参考 sime 的 `max(lm, mixed)` 和 msime 的衰减策略。
10. **简繁与字符集联动**：开了繁体却过滤常用字集，会把港台字形过滤掉；顺序应该是"转换 → 字符集校验 → 过滤"。

### 5.2 英文/中英混输的 8 个点

1. 英文候选不要参与中文整句的词图打分，两套评分体系不可比。
2. 词间空格是状态，不是字符串拼接；退格、光标移动、粘贴都要能正确回退状态。
3. 大小写推导要可预测：句首大写、全大写锁定、驼峰保持原样，三种模式不要互相干扰。
4. URL/邮箱/代码片段要能识别，避免自动加空格和自动大写。
5. 英文拼写纠错要保守：只对"明显手误"（相邻键、漏字母、重复字母）纠，不要改专有名词。
6. 词补全的候选要按词频排，不要按字母序。
7. 中英切换键（Shift/Ctrl+Space）要处理"单击 vs 长按"和"组合键"的冲突，参考 wind 的 `claimShiftTap`。
8. 如果做纯英文 IME，先确认目标用户是否愿意放弃系统 XKB——大多数不愿意。

### 5.3 性能预算（桌面 CPU 参考）

| 环节 | 预算 | 依据 |
|---|---|---|
| 按键 → 首帧 | < 16ms（一帧） | 交互基本要求 |
| 引擎解码（10 字内） | < 5ms | sime 全拼 2.8ms；msime 更快 |
| 词典查询 | < 1ms | mmap + 前缀索引 |
| 神经重排 Top-10 | < 1ms | sime +0.007ms |
| AI 候选（异步） | 100–300ms | bangke p50 89ms + 防抖 200ms |
| 冷启动 | < 300ms | 词库必须 mmap，不能全量反序列化 |
| 常驻内存 | < 80MB | 词库映射不计入 RSS 实际占用时更低 |

### 5.4 工程与合规

1. **线程模型**：一个 session 只能在一个线程用；worker 只写缓存，绝不调引擎/UI API。bangke 的崩溃注释值得反复读。
2. **进程隔离**：网络、语音、剪贴板、LLM 都放独立进程或 provider，用 socket 激活；输入法主进程不持网络栈。
3. **用户数据可迁移**：纯文本或带版本号的二进制 + journal；升级词库时按"代次目录 + 回放"处理，不要原地改基础词库。
4. **只读系统目录**：`/usr/share` 只读，用户数据必须写 `$XDG_DATA_HOME`；打包时不要把词库写进用户目录。
5. **许可**：librime BSD、OpenCC Apache、pinyin-data MIT、五笔 MIT 宽松；ibus-rime GPL-3.0、rime-ice/frost GPL-3.0、essay/plum LGPL-3.0、万象 CC BY 4.0、libpinyin GPL-3.0。**GPL 词库和 GPL 前端会约束你的分发方式，闭源产品要提前规划。** CC BY 需要署名，CC-BY-SA 有传染性。
6. **隐私**：输入法能看到一切。不要记录原始按键；云候选只发当前未上屏拼音；LLM 上下文要明确告知并可关闭；日志脱敏。
7. **测试**：金样（输入序列 → 候选序列）+ 延迟基准 + 真实应用冒烟（GTK/Qt/Electron/终端/浏览器）。CI 里跑不了真实输入法，至少要有 headless 引擎测试。
8. **不要维护三份状态机**：Sime 在 Java/Swift/Fcitx5 各写了一份 composition 逻辑，维护成本很高。把 buffer/selection/context 抽到平台无关层。

### 5.5 常见错误清单

- 把候选窗做成普通窗口 → Wayland 下焦点丢失、位置错乱。
- 在按键线程里等模型 → 输入卡顿，用户直接卸载。
- 用 `commit_history` 当唯一上下文 → 数字/标点/英文被跳过，上下文断裂。
- 用户词库直接改基础词库 → 升级即丢数据。
- 候选排序不稳定 → 用户无法盲打。
- 只测自己的词库，不测真实日志 → 上线后准确率暴跌。
- 忽略 fcitx5 是进程内 addon → 一个段错误让整个桌面失去输入法。
- 词库许可没查 → 产品做完发现不能分发。
